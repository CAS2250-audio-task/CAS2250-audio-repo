# 추론 최적화와 지연시간 해석 추가 인계

이 문서는 23:11 1차 인계 커밋 뒤 수행한 개발자료 기반 추가 검증이다. S01을 최적화 선택에 쓰지 않았다. 실제 게임/스트리밍 응답 지연을 측정한 결과가 아니다.

## FP32 / 분류기 autocast FP16

같은 RTX3090·동일 개발1880음원·같은 전처리와 검출기를 사용하고 분류기 계산 정밀도만 바꿨다. 아래 호출시간은 CPU mel/Burg, 검출, crop/gate, H2D/D2H, 분류를 포함하고 오디오수집/파일IO/모델load는 제외한다.

## 80ms의 의미 정정

현재 모델은 미래16프레임(80ms)의 hidden state를 현재 프레임 정답에 대응시켜 학습했다. 실제 미래 샘플을 제공하는 스트리밍 정책이면 그 문맥을 확보하는 지연이 생긴다. **현재 파일/버퍼 추론 API에는80ms sleep이 없고, 끝의 미확보 미래 특징은 hold로 채운다.** 현재버퍼끝을매번hold로추정하는 실시간 정책은 가능한 별도 추론 조건이며, 현재 전체파일 정확도와 동일하다고 보장할 수 없다.

따라서 `연산23ms+80ms`를 실제 게임 응답시간이라고 확정해 쓰면 안 된다. 수집창/호출주기, 실제 미래를 기다리는지, EOF/버퍼끝 처리, 종료확인과 디코딩을 포함한 게임 측정이 아직 없다. 모델문맥80ms, centered frontend nominal12.5ms, 연산 호출시간은 각각 구분한다.

## 기존 0ms 모델의 추가 개발 대조

추가 학습 없이 기존 causal baseline 검출기를 동일 LS MeanAux500(best475)에 결합했다. 같은1880 개발파형에서 noisy command10 F1 **69.788%**, noise-only FP **22/80**, 원본 F1 **96.492%**, 처리 p50 **21.891ms**였다. 모델문맥은0ms이며 실제게임 지연 측정은 아니다.

현재 soft_time+LSMeanAux의 개발 F177.516%와 비교하면 이 기존0ms 후보는 정확도가 낮다. 다만 증강·loss도 서로 달라7.7%p 차이를 lookahead 하나의 인과효과라고 쓰면 안 된다. 현재 가중치의 lookahead 숫자만0으로 바꾸면 학습한 시간축 대응도 바뀌므로 올바른 causal 모델로 간주할 수 없다.

## 제품 후보 판단

지연이 우선이면 OFF LSMean을 먼저 게임에서 확인하고, Mean+commandCE, LSMeanAux+soft_time을 함께 비교하는 것이 적절하다. OFF는 검출기 미래문맥과Burg가 없고 개발 noise FP가6/80이다. 다만 D3 native 전체입력 모델이므로 실제 게임 입력수집창/호출정책도 공통조건에서 검증해야 한다. 파라미터 수만으로 실제 속도를 추정하지 않는다.
